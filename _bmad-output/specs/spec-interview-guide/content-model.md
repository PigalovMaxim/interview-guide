## Градация

| Вкладка | Редакционный ориентир |
| --- | --- |
| Junior | От базового понятия и простого примера к самостоятельному объяснению типичной ошибки или небольшой задачи. |
| Middle | От уверенного применения механизма к анализу взаимосвязей, диагностики и компромиссов. |
| Senior | Формулировка сохраняется по источнику; редакционный разбор проверяет ограничения, последствия и обоснованный выбор. |
| Сложные вопросы | Углублённые кейсы, нестандартные задачи и неочевидное поведение; целевой уровень указан отдельно, а не выводится из названия вкладки. |

Уровни вопросов взяты из исходных списков обоих источников. Один вопрос EasyOffer может повторяться на уровнях, но имеет отдельный ID и адаптированные объяснение, критерии и перенос. Основной вопрос не заменяется инженерным сценарием ради уровня. Порядок 1…N сохраняет порядок принятого источника внутри группы, сначала EasyOffer, затем GitHub; это не обещание линейного роста сложности.

Пустые сочетания допустимы и честно обозначаются в интерфейсе. TanStack Query не представлен. Во вкладке advanced находятся только сохранённые практические задачи, где targetLevel и angles остаются прежними. Стартовая тема — JavaScript.

## Общая карточка

Редакция 3 заменяет только тематический банк. Все 60 практических карточек сохранены с прежними ID, формулировками и уточнениями. Единственное исправление решения: validCalendarDate возвращает false для нестрокового ввода; остальные поля практических карточек не изменены. Новое интервью использует interview-guide.ratings.v3. Архивы interview-guide.ratings и interview-guide.ratings.v2 не импортируются, не изменяются и не удаляются даже при очистке; ключ оформления прежний.

Происхождение хранится в source отдельно от references редакционного разбора. EasyOffer: provider, sourceId, url, level, listUrl, retrievedAt. ID: easyoffer:{level}:{sourceId}; ссылка /frontend-developer/question/{slug}. GitHub: provider, sourceId, url с закреплённым commit/строкой, level, retrievedAt, commit, path, line; ID из manifest. Даты получения — 16.11.2026, сверки новых ответов — 17.11.2026.

| Поле | Обязательность и смысл |
| --- | --- |
| `id` | Непустой уникальный устойчивый ID; не номер в списке. Смена порядка не переносит оценку на другой материал. |
| `tab`, `topic` | По одному ключу из каталогов выше. |
| `ordinal` | Целое 1…N, уникальное и без пропусков внутри пары `tab × topic`. |
| `kind` | `question`, `case` или `task`; у темы `coding` — `task`. |
| `title` | Самодостаточная формулировка вопроса или название задачи, видимое до раскрытия. |
| `question` | Точная исходная формулировка вопроса без готового объяснения; для практики — сохранённый кейс. |
| `questionCode`, `questionCodeLanguage` | Необязательный кандидатский пример, согласованный с вопросом; не скрытое решение практической задачи. |
| `shortAnswer` | Краткий ориентир ответа для интервьюера. |
| `explanation` | Разбор причин, нюансов и компромиссов; код и примеры там, где помогают объяснению. |
| `assessment` | Три предметных ориентира: `basic`, `confident`, `deep`. Они относятся к этому вопросу и его ожидаемому уровню. |
| `followUps` | Ровно две ветки `{kind, question, expected}`: `support` проверяет отдельный шаг при затруднении, `transfer` меняет существенное условие при уверенном ответе. Вопросы и предметные ожидаемые признаки непустые. |
| `targetLevel` | Для `advanced`: `junior`, `middle` или `senior` как минимальный ожидаемый уровень обсуждения; для остальных определяется вкладкой. |
| `angles` | Для `advanced`: один или оба признака `engineering`, `nuance`. |
| `context` | Версия библиотеки, среда или ограничения, если от них зависит корректность ответа. |
| `source`, `editorial` | Для вопроса: происхождение с уровнем и датой получения; editorial: true означает самостоятельный редакционный разбор. |
| `references`, `verifiedAt` | Источники проверки содержания и дата проверки, заполняемые при подготовке материала. Источники технических ответов — первичная документация или спецификации. |

«Базово / уверенно / глубоко» должны описывать наблюдаемые признаки ответа, а не повторять эти слова. Например, разница может быть между называнием механизма, объяснением причин и обсуждением ограничений с обоснованным выбором. Незнание редкого факта само по себе не определяет общий грейд кандидата.

Уточнения задают по одному после самостоятельной попытки. «Уверенно» требует выполнения всего основного задания и его ограничений, «глубоко» — дополнительно независимого применения в изменённой ситуации. Ответ с помощью не доказывает глубину. Допускаются обоснованные альтернативы, соответствующие контракту. Поле `questionPoints` больше не используется; подсказки не должны находиться в кандидатской части. Все темы банка не являются обязательным экзаменом для определения грейда.

## Дополнение для `task`

| Поле | Содержание |
| --- | --- |
| `statement` | Условие, ограничения, ожидаемый результат. |
| `examples` | Примеры входа/выхода или наблюдаемого поведения. |
| `starterCode`, `language` | Готовый к передаче стартовый код и язык подсветки. |
| `solution` | Объяснение решения и код, отдельно от стартового кода. |
| `edgeCases` | Граничные случаи, которые интервьюер проверяет при разборе. |
| `complexity` | Оценка времени/памяти для алгоритмической задачи; для иной задачи — применимый разбор затрат либо явное объяснение неприменимости асимптотики. |

Видимая кандидатская часть содержит `title`, `question`, `statement`, `examples`, `starterCode`. Краткий ответ, объяснение, решение, критерии, обе ветки уточнений с `expected` и разбор крайних случаев относятся к отдельной части для интервьюера. У задачи раскрытие основной карточки не показывает разбор. Автоматическое и ручное копирование используют только кандидатские поля независимо от состояния раскрытия анализа.

## Проверка наполнения

- 145 уникальных ID, 85 вопросов из двух manifest и 60 сохранённых задач. Пустые группы допустимы; ordinal последовательны в непустых.
- Точное соответствие принятым источникам и уровням, отсутствие отклонённых позиций; дополнение не дублирует основные вопросы EasyOffer.
- Сохранность практики проверяется хешем файла, полных карточек и исходных контрактов из data-sources/coding-preserved.json.
- Нет пустых обязательных полей, заглушек и одинаковых карточек с заменённым названием уровня.
- Основной вопрос EasyOffer может повторяться на разных уровнях; разбор, критерии и перенос должны содержательно различаться.
- Редактор проверяет порядок и межуровневое различие; количество полей и сортировка сами по себе не доказывают градацию.
- Ответы и решения проверены по первичным источникам; примеры задач проверены вне сайта, в подходящей среде. Неоднозначность разрешена через явно описанные условия и допустимые варианты ответа.
- Зависимость от версии или среды не скрывается за категоричным универсальным ответом. Целевые major-версии необходимо выбрать по Q-3.

Редакционные ответы не выдаются за импортированные ответы источников; UI явно обозначает это. Источник вопроса и первичная документация для проверки ответа показываются отдельно. Счётчики и покрытие X/N, включая N=0, вычисляются из фактического банка.
